0:40Independent bug hunt20 min
What

Same method, applied to the real bank-dashboard.html — 10 planted bugs.

How
  • Project bug-hunt-screen.html, step back
  • Remind them to log finds in bug-test-plan.html
Help — hand out if stuck
"Are there any bugs in this code?" "I clicked this button and nothing happened — what could cause that?" "Why might a number show up as NaN instead of a value?"
Answers — all 10 bugs
#BugFix
1Missing closing tagAdd </div> after balance footer
2Invisible balancecolor: #0F1340 → #FFFFFF
3Wrong transaction signCoffee: credit → debit
4Wrong input typetype="text" → type="number"
5Button typoonlick → onclick
6Wrong operatorbalance + amount → - amount
7Element ID typo"balence-display" → "balance-display"
8NaN on empty inputAdd isNaN() check before calculating
9Wrong interest formula* rate → * (rate/100)
10No overdraft checkAdd if (amount > balance) guard
If a group asks Copilot to "fix everything at once": it'll likely miss 8, 9, 10 (missing logic, not broken code) and 3 (a data error, not a syntax one). Use it as a live teaching moment if it happens — stop the room, look at what it missed together.
If Nova's restraint is genuinely too much for one student: only affects that one person since each has their own repo. Rename their .github/copilot-instructions.md on github.com → rebuild their Codespace container → Copilot reverts to normal for them only.

1:13Round 1 — Fix the Bug7 min
What

challenge.js already has a buggy interest-rate function pre-loaded. Ask Copilot Chat to fix it, then prove it with Node.

How
  • Open challenge.js — it's already there, no typing needed
  • Ask Copilot Chat to review and fix it
  • Add console.log(calculateMonthlyPayment(1000, 5, 1));, save
  • Terminal: node challenge.js — see the real number
Help
"Can you review this function for bugs? Pay attention to how the interest rate is being used."
Answer

monthlyRate = annualRate / 12 → should be annualRate / 100 / 12. 5% treated as 5, not 0.05.

If Copilot refuses / flags "SQL injection": shouldn't happen here since the code's already in a real file — but if it does, confirm the function is actually saved in challenge.js before asking Chat about it.

🍽️ Lunch & Accessibility 2:35–3:10
2:35Lunch30 min
What

Accessibility activities happen during this window. No content to run — a genuine break.

Why lunch sits here: before any creation starts, not mid-way through it — groups have a plan sketched but nothing built yet, so nobody's mid-flow when they break.
3:05Accessibility discussion5 min
Say

"You just spent lunch thinking about accessibility. Before we start building — does anything change how you'd want your feature to work? Would everyone be able to use it?"

Prompt if quiet

"Could someone using a screen reader use your feature? Could someone who can't see colour tell your progress bar apart from the background?"

How

1–2 quick reactions, keep it tight — this is only 5 minutes. If a group wants to act on something, that's a legitimate stretch goal.

Build: Feature Creation 3:10–4:35
3:10Feature creation85 min
What

Everyone creates a new file, copies colours/header from practice-feature.html (built in the tutorial). Structure, logic, styling, and testing all happen in this one continuous block — no separate checkpoint or testing slot, so pace it yourself as you circulate.

Rough guide
  • ~3:35 — structure done: heading, inputs, button, opens in Live Server without errors. Ugly is fine.
  • ~4:10 — styled and basic JS working
  • ~4:25 — tested: "Code freeze. Try to break your own feature on purpose — empty fields, negative numbers, huge numbers."
Help by year group
Y9–10: "Why isn't my progress bar changing width?" Y11: "Review this function for edge cases I might have missed" Y12–13: "How would you refactor this to be more maintainable?"
At ~4:00, if any group isn't working yet: "Strip it back. One input, one button, one number on screen." Say it to the whole room.
Close Show & Feedback 4:35–5:00
4:35Show & tell15 min
How

2 min each. Room answers "what did you like?" after each.

If a demo breaks live: "Congratulations — a live demo failure. That's the most authentic developer experience of the day." Show it in the editor instead.
Your closing
"Two hours ago you built one feature together, step by step. Then you described your own idea, Copilot helped you build it, you tested it, you fixed it, you shipped a demo. That loop — describe, build, test, fix — is the actual job. The tools will keep changing. The loop won't."
4:50Feedback10 min
Say
"One word for how today felt" — go round the room fast, no explanations needed.
How

Put a feedback form or QR code on screen if you have one. Keep it short — energy is naturally dropping after demos, so a fast light close beats a thorough one nobody engages with.

If something isn't covered here, it's on the Troubleshooting Card or the "If It All Falls Apart" page. If it's still not covered — you already know more about this than you think you do.
