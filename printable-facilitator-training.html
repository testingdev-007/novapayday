Part 1The Fundamentals
1 — What GitHub actually is

A repository ("repo") is a folder of files where every saved change is kept forever as a numbered commit. You can always go back to any earlier version — nothing is truly lost by editing it.

Your workshop repo contains bank-dashboard.html, starter-template.html, challenge.js, and two configuration files. That's it — a folder with a memory.

Ticking "Template repository" in Settings adds a Use this template button, letting anyone make their own full copy under their own account instantly. That's how every student gets an identical, independent copy without ever touching yours.

Try it
Open your repo, click "commits" near the top of the file list — every upload you've made is there, in order.
Q: If a student breaks their copy completely, is your original affected?
No. Each copy is completely independent.
2 — What a Codespace actually is

Not your computer — a borrowed one. Clicking "Create codespace" starts a real, temporary Linux machine in a data centre, installs VS Code and your devcontainer.json extensions, and streams the editor into the browser. The browser is just a window onto it.

Why this matters
If a Codespace misbehaves, delete it and make a new one — you're not "reinstalling," just asking for a fresh borrowed computer.
Try it
Open a Codespace, open a terminal, type whoami then hostname — confirms it's a real, separate machine.
3 — What Copilot actually does — three modes

Inline completions (Tab-complete) — type a comment, Copilot suggests code as ghost text, press Tab to accept. Prediction, not conversation.

Ask/Chat mode — a proper conversation. Doesn't touch files directly. This is where Nova's Bug Hunt restraint works best — it's built for conversation, not action.

Agent mode — reads and edits files directly, autonomously, multi-step. Nova's instructions still load here, but because Agent mode's whole purpose is to act, it's more likely to just fix things when asked. Nova has an explicit hard rule for this: one real fix, then stop and explain, during the Bug Hunt specifically.

The one thing worth knowing cold
Copilot is confidently wrong a meaningful amount of the time. Always test what it gives you.
Worth testing before Friday
Switch to Agent mode yourself, ask it to "fix the bugs in this file" during a mock Bug Hunt. See if it holds back as intended.
4 — What Nova adds, and why

Nova is not a separate tool — it's .github/copilot-instructions.md, a text file Copilot Chat reads automatically in your repo. It changes behaviour without changing which product students use.

See Part 2 below for the full, evidence-based comparison against plain Copilot.

Part 2Nova vs Plain Copilot — condensed

Same tool, one extra file. Plain Copilot answers from general training with no idea it's talking to a 13-year-old mid-exercise. Nova reads the same repo's instructions file and adjusts.

Evidence — Bug Hunt: "Are there any bugs in this code?"
Plain Copilot
Lists several or all bugs directly — no reason not to.
Nova
"Yes, several! Look at the page first — does anything look wrong? Then use it — click things, type things. What breaks?"
Evidence — off-topic request
Plain Copilot
Just tries to help with whatever's asked.
Nova
"Let's get back to your feature — what part are you working on right now?"
Honest limits

It's an instruction, not a lock — a persistent student could still get more out of it than intended. It doesn't learn during the day — every chat starts fresh from the same file. It doesn't make Copilot more technically correct, only more appropriately toned.

The honest verdict
Nova is genuinely better for this room — not more powerful, more appropriate. It protects the Bug Hunt, gets out of the way during Build, talks to students like students. Not a guarantee against misuse — for a supervised one-day workshop, that's the right bar, and it clears it.
Part 3Full Bug Tutorial — do this yourself
Do this in a real Codespace, not just on paper. This is the exact tutorial students follow. Actually run it before Friday.
The method — four steps, every time

1. Look — open the preview. Does anything look visually wrong?
2. Use — click every button, type in every field. Does something not respond?
3. Read — open the code, read it slowly, line by line.
4. Test — make your fix, save, check the preview again. Don't assume — look.

Worked example (not a real dashboard bug)

A button is supposed to show a greeting. Click it — nothing happens, no error.

1
Look → nothing obviously wrong
The button looks normal. Not a visual bug — move on.
2
Use → confirmed broken
Click it — nothing happens. Now you know where to look.
3
Read → find it
<button onclick="sayHi()">Click me</button>

function sayHu() {   ← should be sayHi
  alert("Hi!");
}
One letter different. JavaScript can't find a function that doesn't exist, so it silently does nothing.
4
Fix + test
Click before the u, delete it, type i. Save (Ctrl+S). Switch to Live Server, click the button — a popup says "Hi!"
Now for real — the actual dashboard

Same four steps, no answers given here on purpose — this is exactly what students see.

Look

Scroll the real preview top to bottom slowly. Anything missing, invisible, or misplaced?

Use

Click every button, type in every field. Then deliberately: leave a field empty, type letters where numbers go, type a negative number, type a huge number.

Read

Open the file, read HTML then CSS then JS, one line at a time. Press F12, check the Console tab for red errors while using the page.

Fix + Test

Click the exact spot, correct it, save, switch to Live Server, redo the same action that was broken. Log it in the Bug Test Plan either way.

Typos in names (read character by character) · colours that hide things · maths that's backwards · missing checks against silly input.
Getting unstuck
"I clicked this button and nothing happened — what could cause that?" · "The console shows this error: [paste it]. What does it mean?" · "I expected X, but Z happened instead. Why?"

Part 5Narrating Live & Common Questions
Narrating this live

You don't need new material — you need confidence. The full script is in the Master Script; what this manual gives you is the ability to say those lines from experience, not cold. You can honestly say "I did this exact tutorial myself" — because you did.

The one habit worth building
When you genuinely don't know an answer, say so and open your own Copilot Chat live, in front of the student, and work it out together.
Common questions you'll get asked
"Is Copilot going to take my job one day?"
It changes what the job looks like — someone still has to know what to ask for and whether the answer's right. That's the skill being taught today.
"Why can't Nova just fix all the bugs for me?"
Deliberate — it hints rather than solves during Bug Hunt. Finding the bug is the point, not just having it fixed.
"Is my code actually running somewhere, or is it fake?"
Completely real — see Part 1, Module 2. A genuine, temporary computer.
"What happens to my Codespace after today?"
It sits idle and gets cleaned up eventually, but the repo — the actual files — stays on their GitHub account permanently.
