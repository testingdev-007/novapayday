Module 1 — What GitHub actually is
🐙
A folder that remembers its own history

Forget "developer tool" for a second. GitHub is a place to store a folder of files — called a repository, or repo — where every saved change is kept forever as a numbered commit. You can always go back to any earlier version. Nothing is ever truly lost by editing it.

Your workshop repo (novapay-workshop) is exactly this: a folder containing bank-dashboard.html, starter-template.html, challenge.js, and two configuration files. That's it. That's the whole "developer" mystique — a folder with a memory.

Why a "template" repository specifically? Ticking "Template repository" in Settings adds one button — Use this template — that lets anyone make their own full copy of your repo, under their own account, instantly. That's how every student gets an identical, independent copy of the workshop files without ever touching yours.

🔗 Try it on the real thing

Open your actual workshop repo on github.com right now. Click the commits link near the top of the file list — you'll see every file you've uploaded, each as its own saved commit, in order. This is the exact repo your students will copy on Friday.

Q: If a student breaks their copy of the repo completely, is your original repo affected?
No. Each student's "Use this template" copy is completely independent. Nothing they do can touch your original.
Module 2 — What a Codespace actually is
☁️
Not your computer. A borrowed one.

When a student clicks Code → Codespaces → Create codespace on main, GitHub doesn't download anything to their laptop. Instead, it starts up a real, temporary Linux computer somewhere in a Microsoft data centre, installs VS Code and the extensions your devcontainer.json lists, and streams the whole editor into their browser tab.

This is why it works identically on a school Chromebook, an old laptop, or your own machine — the actual computing happens elsewhere. The browser is just a window onto it.

Why this matters for you as facilitator
If a Codespace misbehaves, deleting it and creating a fresh one costs nothing — you're not "reinstalling" anything, you're just asking for a new borrowed computer. This is why the rescue advice throughout your materials is always "delete it, make a new one" rather than trying to repair it.
🔗 Try it on the real thing

Open a Codespace on your own test repo. Once it loads, open a new terminal (Terminal → New Terminal) and type whoami then hostname. You'll see this is a real, separate Linux machine — not your laptop.

Module 3 — What Copilot actually does
🤖
Three modes people lump together as one

Inline completions (Tab-complete) — you type a comment describing what you want, and Copilot suggests code as grey "ghost text." Press Tab to accept. This is prediction, not conversation — it's reading the surrounding code and guessing the most likely continuation.

Ask/Chat mode — a proper conversation. You ask a question in plain English, it answers, you can ask follow-ups, but it doesn't touch your files directly. This is where Nova's restraint during the Bug Hunt works best — it's designed for conversation, not action.

Agent mode — a different beast entirely. Instead of just talking, it reads and edits files directly, autonomously, across multiple steps, with far less friction. Nova's instructions still load here too — but because Agent mode's whole purpose is to act, it's noticeably more likely to just fix things when asked, even with the same restraint instructions present. Nova's file has an explicit hard rule for this now: one small change, then stop and explain, during the Bug Hunt specifically.

Worth testing yourself before Friday
Switch to Agent mode in your own test Codespace and ask it to "fix the bugs in this file" during a mock Bug Hunt. See whether it holds back as intended, or fixes several bugs in one go. Either way, you'll know what to expect from students discovering the mode switch.
The one thing worth knowing cold
Copilot is confidently wrong a meaningful amount of the time. It's pattern-matching against code it's seen before, not reasoning about your specific problem from scratch. This is the single most important thing to model for students: always test what it gives you, never trust it blindly.
🔗 Try it on the real thing

In your test Codespace, open a blank line in any file and type // function that adds tax to a price then wait for the ghost text, then press Tab. Then open Ask mode and ask the same thing as a question instead. Then try Agent mode. Notice how differently all three feel.

Module 7 — Narrating this live to the room
🎤
You don't need new material — you need confidence

Everything you say on the day is already scripted in printable-session-day.html. What Modules 1–6 give you is the ability to say those lines from experience rather than reading them cold. That difference is what removes the fear.

  • When you introduce the bug hunt, you can honestly say "I did this exact tutorial myself" — because you did
  • When someone's stuck on a bug, you'll likely recognise the shape of the problem from your own run-through
  • When the build phase reaches Step 7 and someone's progress bar animates for the first time, you'll know exactly why that moment matters
The one habit worth building
When you genuinely don't know an answer, say so and open your own Copilot Chat live, in front of the student, and work it out together. You've now done this enough times in Modules 5–6 that it won't feel like exposure — it'll feel like exactly what you'd do anyway.
Module 8 — Common questions you'll get asked
"Is Copilot going to take my job one day?"
A fair, honest answer: it changes what the job looks like, but someone still has to know what to ask for and whether the answer's right — that's the actual skill being taught today.
"Why can't Nova just fix all the bugs for me?"
It's deliberately designed to hint rather than solve during the Bug Hunt — you can say this outright, it's not a secret. The point is finding the bug, not just having it fixed.
"Is my code actually running somewhere, or is it fake?"
Completely real — refer back to Module 2. It's a genuine, temporary computer, and Live Server is a genuine local web server running on it.
"What happens to my Codespace after today?"
It'll sit idle and eventually get cleaned up automatically after a period of inactivity, but their repo (the actual files and code) stays on their GitHub account permanently, and they can always create a fresh Codespace from it later.
